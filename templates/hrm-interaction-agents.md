# HRM interaction pilot dispatcher

Use this profile only for a project explicitly adopting `ap-hrm-interaction/1`.
Record the exact AP source revision and project-owned milestone when adopting it.
This template does not activate itself or replace another repository's policy.

## Roles and continuation

- GPT-6 Astra owns outcome interpretation, requirement reconciliation, work commissioning, technical escalation, and review presentation.
- GPT-5.6 Sol workers own bounded investigation and implementation. A fresh GPT-5.6 Sol reviewer checks consequential changes independently of the builder's conversation.
- The local kernel records commands and enforces their structural authorization, ownership, revision, and evidence conditions. It does not determine business truth or run models.
- An operator instruction to implement an in-scope change supplies that direction. Do not request approval for the same implementation again. Record the instruction and its source before commissioning the work.
- Missing files, adapters, exported symbols, or ordinary technical choices go to the orchestrator for investigation or an amended work order. Ask the operator only for the unresolved business meaning or authority that remains after investigation.
- Keep original question, answer, source message, interpreted effect, and revision together. A later correction supersedes an earlier interpretation; it does not erase it.

## Review and changes

- Keep one milestone open through review and remediation. Work attempts and milestone acceptance have separate states.
- During a presentation batch, retain the live preview and the worker's relevant context. Do not create a commit, PR, independent review, or full test run for each visual adjustment.
- Direct operator feedback in a worker task must be recorded as an operator intent by a trusted adapter before the revised assignment is applied. The current CLI pilot requires the orchestrator to submit that amendment; direct task capture is not implemented yet.
- Multifile corrections are ordinary work orders. Changes to accepted requirements use an explicit operator intent and revise the milestone while retaining its review history.
- Workers may not silently expand scope. The orchestrator can commission an authorized change within the adopted path/effect policy. Unaffected work remains available; changed evidence must be refreshed.
- A current review request names the current milestone and work-order revisions. Only the operator accepts or defers it. A stale review cannot close newer work.

## Boundaries and reporting

- This pilot authorizes local repository work only. Deployment, provider mutation, customer transmission, money movement, credentials, and production activation require their existing separate controls; a decision record alone executes none of them.
- Project merge-release policy remains in force. Routine implementation permission does not waive an existing exact-head merge gate.
- Return compact role projections and relevant evidence references. Keep full source messages and the ledger private. Do not count a model-labelled approval as proof that human input was necessary.
- Report unavailable host-token measurements as unavailable. Do not treat artifact byte counts as total model context or local checks as deployed behavior.
